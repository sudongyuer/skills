# Choosing the form

Recommend one form at Gate 2 with the evidence from the feasibility study.
Both forms run the same phases; they differ in constraints.

| | Pure Swift / SwiftUI | RN / Expo + one Swift kit module |
| --- | --- | --- |
| Best when | iOS-only, system feel is the product, small team that reads Swift | UI iteration speed matters, shared TypeScript logic or web reuse, hot reload, OTA updates |
| Risk | Slower UI iteration; no OTA | JS dependencies that do not bundle in Metro; fake-native UI; bridge overhead on hot paths |
| UI rule | SwiftUI by default, UIKit where SwiftUI cannot meet HIG (lists, text, navigation chrome) | RN for screens; native kit for anything RN cannot render at system quality (lists, chat/text, inputs, navigation bar items) |
| Verification | XCUITest or AXe driving the Simulator; Swift unit tests | Node tests for logic; AXe/Simulator UI checks; Swift checks for the kit |
| Delivery | TestFlight via CI | TestFlight via CI; OTA only when the native fingerprint is unchanged |

## Constraint set — pure Swift / SwiftUI

- iOS only. No Android or cross-platform abstractions "for later".
- Minimum iOS version: <from interview>.
- Swift concurrency for async work; UI updates on the main actor.
- System components and semantic colors first; never imitate a control the
  platform provides.
- Credentials in Keychain only.
- Never disable code signing, including Simulator builds.
- Generated files (`*.xcodeproj` from a generator, if used) are never edited by hand.

## Constraint set — RN / Expo + Swift kit

- iOS only. Do not add Android implementations, fallback stubs, or Android build scripts.
- All first-party native code and native UI live in one kit module, registered
  through one module facade; no separate bridge packages.
- When RN cannot meet a UI requirement at system quality, implement it in
  Swift in the kit instead of approximating it in RN.
- `ios/` is generated by prebuild; persist changes in app config, config
  plugins, or the kit — never only in generated files.
- Import native APIs only through the kit's typed facade; remove event
  subscriptions on unmount.
- Never disable code signing, including Simulator builds.
- Dependencies found not to bundle in Metro are named in `AGENTS.md` with the
  finding that excluded them.
- Read the versioned docs of the installed Expo / RN release before writing
  code; APIs change between SDKs.

## Signals from the feasibility study

| Finding | Push toward |
| --- | --- |
| A required SDK is Node-only or does not bundle in Metro | Pure Swift, or RN with the SDK isolated (native or an offscreen WebView runtime) |
| Most screens are lists, text and forms that must feel native | Pure Swift, or RN with those components in the kit |
| Logic or data layer already exists in TypeScript | RN / Expo |
| The user reads Swift comfortably and wants to | Pure Swift |
